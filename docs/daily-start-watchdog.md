# 정규 수집 미시작 보완

정규 수집 예약(한국시간 평일 18:30)과 실패분 재시도(21:00)는 변경하지 않는다.
GitHub 예약 실행이 생성되지 않은 경우를 위해 `daily-start-watchdog.yml`을 추가한다.

2026-10-22의 18:30 예약은 실제로 19:04:12 KST에 생성됐다
([예약 실행](https://github.com/0baselabkim-debug/qweasd/actions/runs/39760291133)).
그전에 18:50:11에 수동 요청한
[정규 수집](https://github.com/0baselabkim-debug/qweasd/actions/runs/39758472001)이
실행 중이므로 예약 실행은 공유 concurrency에서 대기했다. 예약 발동 지연을
확인했으며 GitHub 내부 지연 원인은 확인되지 않았다.

- 평일 18:45, 19:15에 점검한다.
- 기존 공시 워크플로 완료 이벤트에서도 점검한다. 공시 성공 여부와 무관하지만
  main 및 같은 저장소에서 발생한 이벤트만 허용한다.
- 실제 점검 시각이 평일 18:45 이상 21:00 미만일 때만 동작한다.
  지연돼 다음 날 실행된 점검은 수집을 호출하지 않는다.
- 최신 main 게시 원장을 GitHub에서 읽고 당일 게시 완료이면 종료한다.
- main의 정규 수집이 실행·대기 중이면 종료한다. 오늘 18:30 이후 실행 기록이
  하나라도 있으면 성공/실패/취소/휴장 여부와 무관하게 추가 실행하지 않는다.
  실패분 재시도는 기존 21:00 작업에 맡긴다.
- 실행이 없을 때만 원장과 실행 목록을 재확인하고 기존
  `daily-dashboard.yml`의 `mode=collect`를 main에서 호출한다.
- API 조회 오류·불완전한 상태 응답은 보완 실행을 차단한다. GitHub 요청을
  자동 반복하지 않는다. 요청 접수를 수집 성공으로 표시하지 않는다.

휴장일은 평일 계산으로 추측하지 않는다. 실제 수집기가 기존 공식 KIS 달력으로
먼저 확인하고 휴장일에는 종목 수집을 하지 않는다. watchdog 자체는 시장 API,
API 인증키, DB를 사용하지 않는다. `GITHUB_TOKEN`의 Actions 쓰기는 기존 수집
워크플로 dispatch에만 사용하며 별도 계정·토큰은 만들지 않는다.

점검 자체는 `daily-start-watchdog`로 직렬화한다. 요청 직후 원래 예약이 뒤늦게
생성되는 경쟁은 완전히 원자적으로 방지할 수 없다. 실제 수집은 기존
`kis-validation-auth` 직렬화와 게시 원장·성공 체크포인트 재사용으로 보호한다.
진행 중 작업을 취소하거나 강제 재수집하지 않는다.

각 점검은 Actions Summary 및 30일 artifact `watchdog-results/check.json`에
점검 시각, 기준일, 원장 blob SHA, 관련 실행 ID, 판단·dispatch 여부를 남긴다.
운영 main에 점검 결과 커밋을 추가하지 않으므로 수집 게시와 충돌하지 않는다.

## 수동 확인

저장소 → Actions → Daily collection start watchdog → Run workflow → main.
`dry_run=true`(기본값)는 상태만 확인하고 수집을 요청하지 않는다.
현재 진행 중인 정상 수집에서 실제 guard를 확인할 때도 중복 수집은 차단된다.

## 한계

두 예약과 공시 완료 이벤트는 모두 GitHub에 의존한다. GitHub 전체 예약·Actions
장애에서는 점검도 늦어질 수 있으므로 정시 실행 보장은 아니다. 더 강한 보장이
필요하면 별도 외부 감시 서비스가 GitHub 실행·게시 상태를 확인하고 dispatch하는
구조가 필요하다. 이번 변경에 외부 서비스·새 자격 증명은 포함하지 않는다.

시작 후 실패·지연, KIS/KRX 가격 충돌, 수집된 자료의 정확성은 이 점검의 범위가
아니다. 기존 원천 검증과 21:00 재시도 정책을 유지한다.
