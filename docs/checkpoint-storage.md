# Daily checkpoint transport

`persist_daily_checkpoint.py` keeps the collector's `successes.jsonl` unchanged
locally and in the workflow artifact. Only the checkpoint branch representation
changes. It compresses the exact bytes with deterministic gzip (mtime zero),
without parsing or rewriting JSON, and checks the actual compressed size.

Each Git transport file is at most 90 MiB. A larger gzip stream is split into
ordered `successes.jsonl.gz.part-000000` files. `successes.manifest.json` records
the format version, original and compressed byte counts and SHA-256 digests,
and each part's index, path, byte count and digest. Oversized manifests, bundles
or diagnostics fail before Git publication; diagnostics are never discarded to
make a push fit. Existing parent diagnostics are retained.

The isolated Git index explicitly removes the old plaintext journal and all old
transport parts when replacing the journal. Neither the running checkout nor
its original index is changed. Pushes remain non-force, and a concurrent change
rejects the push. No history rewrite is needed.

`python scripts/checkpoint_storage.py --ref FETCH_HEAD` restores the original
journal, validating all part names/order, sizes and hashes, then the combined
compressed stream and restored bytes. It writes the output only after validation.
Legacy branches containing only plaintext are supported. A damaged new format
(including parts without a manifest) never falls back to stale plaintext.
`daily_checkpoint.Journal` still performs the existing row hash, trade-date,
conflict and interrupted-tail checks; this transport does not change them.

The dashboard CI runs `tests/test_daily_checkpoint_storage.py` as part of the
full test suite, alongside the existing Journal and publication regressions.

## Saved artifact recovery is a separate operation

Do not use `verify_saved` to claim recovery of a new trading date: it selects
the published manifest date and research replay bundle and calls the calendar API.
For a saved-artifact recovery, first verify the artifact ZIP digest and size,
then its bundle date, complete status and success/exclusion/failure counts.
Keep the ZIP, original journal, bundle and diagnostics. Use a separate checkout
of current main to run `prepare_daily_publish.py`, the existing regressions, and
`stage_daily_publication` without collecting or making market API calls.

Before staging or pushing, re-read main's publication ledger and all repository
Actions runs, filtering the exact `.github/workflows/daily-dashboard.yml` path.
Treat requested, queued, waiting, pending and in_progress as active. Do not
publish a competing recovery while an operational run is active, cancel it,
or dispatch a new collection. If the target date is already normally published,
skip recovery. Final publication requires checking generated manifest, validation,
ledger and briefing source hashes and dates. Decision-support is generated by its
own workflow; report its actual generation separately. A successful workflow alone
is not evidence that the app has loaded a new snapshot.
