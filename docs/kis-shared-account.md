## 확인한 충돌과 선택한 정책

저장소별 concurrency와 장중의 조용한 실행 상태 조회는 조회-실행 사이 경쟁을
막지 못한다. 현재 활성 실행이 없다는 사실도 다음 OAuth 발급을 막지 못한다.
재발급 영향이 불명확한 동안 별도의 토큰 두 개를 병렬로 사용하지 않는다.

처음 구현한 정책은 **인증부터 마지막 응답까지 하나의 배타적 세션**이다.
전체시장 세션 중 장중 작업은 즉시 `shared_lock_busy`로 거절하며, 반대 경우도
같다. 실행 중 작업을 취소하지 않고, 장시간 대기나 자동 재수집을 만들지 않는다.
장중 수동 조회가 90~105분 동안 무조건 대기할 필요는 없지만, 같은 시간에
안전하게 호출할 근거가 확보되지 않아 현재는 동시 사용을 허용하지 않는다.
추후 인증 잠금과 호출량 조정을 분리하려면 공유 토큰 수명·재발급 효과·전체
행위자·공급자 한도 확인과 별도 검증이 필요하다. 새 계정/앱키는 요구하지 않는다.

## 공통 잠금 구현

양쪽에 바이트 단위로 같은 `kis_shared/`를 둔다.
중앙 저장소는 기존 qweasd, 운영 예정 브랜치는 `kis-shared-account-state`다.
실제 운영 잠금 브랜치는 소유자 없는 빈 상태로 초기화·원격 재검증했다.
운영 호출은 활성화하지 않았다. 상태에는 계정 비밀이나
토큰 대신 소유 저장소·Run ID·커밋·임의 lease ID·획득/만료·순번만 기록한다.

1. 중앙 브랜치의 실제 tip을 조회한다. 실패 시 캐시로 호출을 허용하지 않는다.
2. 해당 커밋을 부모로 새 상태 커밋을 만들고 일반 fast-forward push를 수행한다.
   같은 부모의 두 자식은 동시에 tip이 될 수 없다. force/reset/delete는 없다.
3. 원격 readback까지 일치해야 획득 성공이다. 응답 불명도 호출 권한이 아니다.
4. OAuth와 시장 요청 직전에 새 원격 tip, 소유권, 만료까지 남은 요청 시간,
   세션 내 자격 결합과 실행 주체를 확인한다. 패자는 물리적 요청을 하지 않는다.
5. 정상 종료 시에만 해제한다. 예외·실패 전체시장 보고·강제 종료·만료는 소유권을
   남긴다. 만료만으로 빼앗지 않는다. 프로세스가 계속 실행 중일 수 있기 때문이다.

소유 TTL은 최대 190분이며, 기존 전체시장 대상일/170분 HTTP 창은 확대하지 않는다.
강제 종료 복구는 자동 등록하지 않았다. `recover`의 별도 명시적 경로는 고정
revision, 만료 후 60초 격리, 정확한 소유 Run의 terminal/commit, 모든 worker와
외부 발급자의 중단 증거를 요구한다. 실제 Actions 조회를 하는 검증자와 운영자
승인 없이 호출하지 않는다. 이 함수의 단위 테스트를 실제 장애 복구 성공으로
표시하지 않는다. 관리자 강제 push·브랜치 삭제·프로토콜 미참여자는 보호 범위
밖이므로 전체 행위자 등록과 중앙 브랜치 보호 설정 검토가 필요하다.

Git Contents API SHA 조건부 쓰기는 파일 단위 경쟁에 사용할 수 있지만, 본
구현은 Git 커밋 부모와 fast-forward 규칙을 사용한다. 무조건적인 Git refs
갱신이나 저장소 간 동일 concurrency 이름에는 의존하지 않는다. 외부 서버나
유료 서비스, 토큰을 저장하는 Git 브랜치는 만들지 않았다.

## 인증·호출량

기존 `KIS_APP_KEY`/`KIS_APP_SECRET` 이름을 재사용하도록 개발 워크플로 참조만
변경했다. 실제 값은 읽거나 변경하지 않았다. 독립 계정 전용 Secret은 요구하지
않는다. qweasd의 기존 운영 main 참조는 아직 변경하지 않았다.

발급은 세션당 최대 1회이며 실패·결과 불명도 소진한다. 발급 예약을 먼저 기록하고
정상 인계 뒤에도 60초의 인증 격리를 둔다. 토큰은 메모리에만 존재하고, 서버의
실제 만료 필드와 duration 중 짧은 쪽을 사용한다. 만료 필드의 시간대는 검토된
설정이 필요하며 임의 추정하지 않는다. 기존 토큰도 만료가 불명확하면 차단한다.

전체시장 1.05초, 장중 2초 간격과 원래 budget/timeout/복구 정책은 유지한다.
공통 세션은 한 번에 한쪽만 호출하므로 참여자끼리 요청량을 합산해 초과하지
않는다. 인증 오류를 재시도하지 않고, 429/5xx를 핑계로 한도를 확대하지 않는다.
성공 원문 복원·실패 요청 한정 복구 알고리즘은 그대로다.

동적 종목 수 N 기준 당일 마스터/거래일/인증/지수 포함 기본 요청은 `2*N+6`이다.
예시 N=2,348이면 4,702회이며 2,348을 고정 상수로 사용하지 않는다. 기존
준비 4회/전체시장 5,600회 상한은 늘리지 않았다. 과거 실측 90~105분에 새 잠금
검사 비용이 추가된다. 원격 tip 조회를 매 요청 수행하므로 Git 통신 지연·제한과
170분 내 완료 여부는 추가 실측이 필요하다. 기존 성능을 보장하지 않는다.

## GitHub 권한과 적용 차단

현재 환경의 공식 `gh api`는 API 호스트 네트워크 정책에서 Forbidden이다.
Git의 정상 인증 도우미 경로는 두 저장소 읽기/개발 브랜치 쓰기와 진단 브랜치
실험에 사용 가능하다. 이를 Actions 실행 토큰의 권한이라고 해석하지 않는다.

qweasd 실행 토큰은 원래 own-repo Contents write/Actions read를 사용한다.
장중 실행 토큰은 own-repo 범위이며 qweasd의 중앙 상태 브랜치 쓰기가 검증되지
않았다. 기존 `OPERATIONS_READ_TOKEN`이 쓰기 가능한지도 확인하지 않았다.
기존 Secret을 확대하거나 새 토큰을 만들지 않았다.

다음이 승인·검증되어야 운영 반영/차단 해제를 진행할 수 있다.

- 중앙 저장소의 Contents write를 양쪽 runtime에서 사용할 최소 권한 자격.
  필요 시 중앙 저장소만 선택한 fine-grained token 또는 GitHub App을 비교한다.
  Contents write는 브랜치 한 개로 제한되는 권한이 아니므로 중앙 main 등 보호
  규칙과 발급·설정 범위에 대한 별도 승인이 필요하다. 기존 KIS 자격은 유지한다.
- 실제 Actions 두 실행 주체의 읽기/경쟁/해제 테스트. 복구 검증 주체에는 소유
  저장소 Actions read가 필요하다. 현재 권한으로 확인되지 않은 권한을 추가하지 않는다.
- 구 수동 KIS 워크플로 및 PC/다른 저장소 발급자까지 참여 여부 검토. qweasd에는
  공유 모듈을 통하지 않는 기존 수동 inline 요청과 `scripts/kis_public_client.py`
  등이 남아 있다. 운영 코드·브리핑을 임의로 바꾸지 않았으므로 전체 행위자 등록은
  미완료이며, 단순 설정 변경으로 이 사실을 해결했다고 표시하면 안 된다.
- 별도로 승인된 최소 OAuth/시장 호출 검증으로 발급 영향·만료·한도 확인.
  현재 승인에는 실호출이 없으므로 이를 수행하지 않았다. 최소 시험 전용 허가와
  실행 경로를 검토한 후 수행하며, 전체시장 호출을 검증용으로 시작하지 않는다.

공유 설정의 `enabled`, 전체 행위자/양쪽 배포/실권한/실KIS검증 증거는 모두 false다.
정기 profile의 `verified`도 false다. true 하나만으로는 세션·원격 소유권·실제
HTTP guard를 통과할 수 없다. 양쪽 main 반영은 보류했고, 현재 cron 및 기존
차단 상태는 그대로다. 실제 수집 성공이나 공유 운영 READY를 주장하지 않는다.

## 보존과 검증 증거

`reports/shared-account/`에 원격 잠금 증거, 원본 보호 검사, 오프라인 결과를 둔다.
장중 저장소의 같은 증거는 `validation/shared-account/`에 둔다.
진단용 `kis-shared-probe-*` 브랜치는 원본과 함께 보존하며 운영 슬롯으로 쓰지 않는다.
두 진단 경쟁은 서로 반대 저장소가 승자가 됐고 각각 패자 0 HTTP, 정상 해제를
확인했다. synthetic 소유 ID를 쓴 메타데이터 시험이며 실 Actions 인증 시험이 아니다.

기존 운영 데이터·세대·DB/JSON/manifest·필터·최종성·검증 규칙은 변경하지 않았다.
20:30 외 수집/복구 예약을 만들지 않았고 Word 브리핑 예약도 수정하지 않았다.
dot 저장소의 실제 22:30 예약 상태는 이번 두 저장소 조사만으로 확인할 수 없다.
