# 2026-10-22 게시 후 수동 검증 절차 — 아직 실행하지 않음

사용자가 코드를 수정할 필요는 없다. 아래 절차는 **승인 후 Codex가 수행할 실행 순서**다. 현재 승인 범위는 과거 보존 자료의 오프라인 시험까지다. 새 날짜 시장 API, 실제 10/22 수동 검증, 신호 등록, 자동 예약은 실행하지 않았다.

## 1. 승인 범위를 먼저 분리

- 10/22 정상 게시본을 읽어 연구용 수동 검증하는 승인.
- 보존된 공식 응답이 없을 경우 KRX KOSPI/KOSDAQ 10/22 일괄 요청 **각 1회, 총 2회** 승인. 이번 구현에는 시장 API 클라이언트가 없으며 기존 승인된 수집 경로를 사용해야 한다.
- 연속 40일 보완이 필요하면 시장·날짜별 누락 목록을 제시하고 별도 승인. 현재 10/20 검증 구간의 기본 누락은 35일×2시장=70회다. 새 기준일에서 다시 계산한다.
- 실제 신호 등록 및 예약 실행은 수동 검증 승인과 별개다. 기존 두 종목 재조회 예산 5회는 이미 소진됐으므로 다른 조회에 재사용하지 않는다.

## 2. 정상 게시본을 커밋 단위로 고정

운영 정기 수집이 게시 완료한 커밋을 고정하고 연구 입력 폴더에 다음을 복사한다. 운영 파일 자체를 수정하지 않는다.

- `snapshot/dashboard.duckdb`
- `snapshot/manifest.json`
- `snapshot/daily-validation.json`
- `snapshot/publication-ledger.json`
- `snapshot/briefing/index.json` → 연구 입력의 `index.json`
- 실제 원본 체크포인트와 원본 수급 재현 자료, 기업행사·제외 상태 근거
- `source.json`: 정확한 커밋, 커밋 시각, 연구 입력 확보 시각(현재 시각을 과거로 지정하지 않음)

`safe_publication_check`가 DB 해시, 날짜, 원장·검증·브리핑 dataset_id/해시, 실제 수급 행 수를 확인한다. 실패하면 별도 오류 저장소에만 기록하고 기존 신호는 유지한다. 단순 workflow 성공을 정상 게시 증거로 대신하지 않는다.

## 3. 원본 및 공식 가격 등록

- `Vault.capture`로 최초/후속 KIS 및 공식 KRX 응답을 원본 바이트 그대로 저장한다.
- KRX 응답의 실제 HTTP 상태·요청 날짜·시장·수신 시각·원문 SHA-256을 대조한 후 `OfficialIndex.add`로 등록한다. 읽을 수 있는 응답이라고 정확한 자료로 판정하지 않는다.
- 정기 체크포인트는 `checkpoint_observation`으로 같은 날짜의 전체 일봉을 선택하고 `assess`로 6필드를 비교한다.
- 후속 레코드가 없고 최초 전체 일봉이 이미 정확히 일치한 경우만 재사용한다. 불량 응답이나 새 충돌은 이 규칙으로 우회하지 않는다.
- 보존된 공식 버전들이 서로 다르면 보류한다. 기업행사 근거 없는 원/수정 차이도 보류한다.

## 4. 40일 문맥과 수급 묶음

- `verify_session_sources`로 KIS 공식 지수의 거래일 원문과 휴장일 원문을 재현한다. 달력 원본 해시·실제 관측 시각을 보존한다. 평일을 임의로 거래일로 만들지 않는다.
- `official_context`로 공식 원시세 40일 및 연속 이전 문맥을 구성한다. 거래정지·상장일·공식 자료 누락·공식 버전 충돌은 보류한다. 서로 다른 기준의 OHLCV 필드를 섞지 않는다.
- 기존 `price_link`의 원본 수급 20일 재현/해시 확인 및 `make_forward_bundle`의 수용 검사를 유지한다. 원본 수급 금액·수량과 DB를 대조한다.
- 기존 스냅샷 가격과 새 공식 문맥이 충돌하면 `build_signal`의 겹친 기간 검사가 계속 차단한다. 공식 종가 하나로 DB를 교체하거나 검사를 끄지 않는다. 새 공식 전체 일봉으로 별도 연구 입력을 만들 필요가 있으면 원본/후보/데이터셋 해시를 분리한 연결을 먼저 검증한다.

## 5. 등록 준비 검사

`prepare_snapshot(snapshot_directory, contexts, bundles, calendar, research_vault)`를 실제 시스템 시각으로 호출한다. 이 함수는 **신호를 등록하지 않는다**.

각 종목의 결과는 `registration_ready_requires_separate_execution`, `condition_not_met`, `no_new_event`, `hold`로 구분된다. 준비 후보도 `record_kind=prospective_preparation`, `pit_eligible=false`이며 실제 전향 성과 표본에 들어가지 않는다.

기준일 공식 가격, 전체 40일 근거, 원본 수급, 공식 달력과 시각이 모두 기존 검사까지 통과해야 준비된다. 과거 신호를 소급 생성하지 않는다. 보존 달력에는 **10/23 개장일**이 있으나, 휴장일 응답이 모든 특별 개장시각까지 증명하는 것은 아니다. 기존 일반 거래일 09:00 KST 등록 시한을 유지하며 특별 일정이 있으면 공식 근거 확인 전 보류한다.

## 6. 검증 후 보고 및 다음 승인

- 종목별 가격 통과/보류, 40일 구성 가능, A/B/C/D 준비 후보, 조건 미충족/자료 부족을 각각 보고.
- 원본 해시·준비 시각·신규 호출량·실측 소요시간·누락 목록을 제출.
- 실제 신호를 기록하려면 별도 승인 후 기존 append-only 저장소·중복 신호 방지 기능에 공식 문맥/출처 해시를 함께 연결. 준비 자료를 실제 신호로 이름만 바꾸어 저장하지 않음.
- 등록 시한이 지났으면 준비 결과를 과거 연구로만 보존하고 다음 신규 거래일을 기다림.

## 운영 연결 원칙

향후 자동화는 운영 정상 게시 이후 연구용 단계로 분리한다. 연구 검증 실패로 정상 수급 게시를 취소하거나 운영 데이터를 덮어쓰지 않는다. 기존 인증 직렬화·운영 우선 정책을 재사용하되, 이번에는 워크플로·cron을 추가하거나 수정하지 않았다.
